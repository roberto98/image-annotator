## [2026-01-28] US-001: Consolidate Dual State Systems

### What was done
- Moved STATE proxy creation from `state.js` into `store/index.js` so the Store module is the single source of truth
- `state.js` now only handles initialization (loading server data into store) and defines COLORS constant
- STATE is created via `window.STATE = createStateProxy(store)` in store/index.js
- Enhanced proxy `set` handler to properly capture `prevState` before mutation (previously passed `null` to `_notify`)
- All state changes are logged when debug mode is enabled via `window.setStoreDebugMode(true)`
- Undo/redo verified working across points, polygons, and figures

### Acceptance Criteria Status
- [x] All state management uses the Store class from store/index.js
- [x] Legacy STATE object in state.js is removed or aliased to Store
- [x] State changes are logged for debugging
- [x] Undo/redo works consistently across all annotation types
- [x] No regression in existing functionality
- [x] Typecheck passes (no JS console errors)

### Key decisions
- Kept explicit `saveToHistory()` pattern rather than auto-saving on every STATE property set. Auto-saving would break drag/zoom operations that set properties many times per frame.
- STATE is still a Proxy (not removed) for backward compatibility - all 9+ JS files use `STATE.property` syntax. The proxy routes through the Store.

### Files changed
- `app/static/js/store/index.js` - STATE proxy created here, enhanced set handler with prevState capture
- `app/static/js/state.js` - Simplified to initialization + COLORS only

## [2026-01-29] US-002: Unify Coordinate Transformation Logic

### What was done
- Connected the existing (but unused) `Viewport` class in `services/viewport.js` to STATE and DOM
- Added auto-linking at module load: viewport reads zoom/translate/dimensions from STATE proxy
- Added `services/viewport.js` to the HTML template load order (after `dom.js`, before `utilities.js`)
- Replaced all coordinate utility function calls across 3 files with viewport methods:
  - `eventToImageCoords(e)` → `viewport.eventToImage(e)`
  - `imageToDisplayCoords(x, y)` → `viewport.imageToDisplay(x, y)`
  - `displayToImageCoords(x, y)` → `viewport.displayToImage(x, y)`
  - `isWithinImageBounds(x, y)` → `viewport.isWithinBounds(x, y)`
- Removed 4 duplicate coordinate functions from `utilities.js`

### Acceptance Criteria Status
- [x] All coordinate transformations use services/viewport.js
- [x] Duplicate functions removed from utilities.js
- [x] Click positions translate correctly at all zoom levels (tested at 100%, 150%)
- [x] Annotations render at correct positions after zoom/pan
- [x] Typecheck passes (no JS console errors)

### Key decisions
- Auto-link viewport to STATE/DOM at module load time rather than in `initializeApp()`. Since viewport.js loads after store/index.js and dom.js, both globals are available. This avoids needing to thread initialization order through the app.
- Kept the Viewport class configurable (dependency injection via linkState) for testability, while also auto-linking for production use.

### Files changed
- `app/static/js/services/viewport.js` - Added auto-linking to STATE and DOM after singleton creation
- `app/static/js/utilities.js` - Removed 4 duplicate coordinate functions (eventToImageCoords, imageToDisplayCoords, displayToImageCoords, isWithinImageBounds)
- `app/static/js/interactions.js` - Updated 5 call sites to use viewport methods
- `app/static/js/rendering.js` - Updated 10 call sites to use viewport methods
- `app/static/js/figures.js` - Updated 9 call sites to use viewport methods
- `app/templates/multi_landmark.html` - Added viewport.js script tag
